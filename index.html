Sub-tutorial · Maven + Angular

Angular dev cycle with Maven only

From "the frontend-maven-plugin packs Angular into the WAR" to a full daily development setup — on a machine that has nothing but Java and Maven.

Many Jakarta EE teams already use the frontend-maven-plugin ("eirslett plugin") to build an Angular app and package it into a WAR. That solves the build. This tutorial adds the development cycle on top of it:

  • the Angular dev server (ng serve) with live reload and hot module replacement,
  • REST calls from the dev server forwarded into the running Jakarta EE 10 container,
  • a container dev mode that redeploys Java changes automatically,
  • the Angular CLI (ng generate, ng update, …) and pnpm for daily work,
  • unit tests in the build and in watch mode,

…without anyone installing Node.js, pnpm or the Angular CLI by hand. Maven downloads a pinned Node.js and pnpm into the project; the Angular CLI is an ordinary dev dependency in node_modules. Nothing is installed globally.

Verified setup. Every command in this tutorial was run against a sample WAR project with: Maven 3.9.14 · frontend-maven-plugin 1.15.1 · Node.js 24.15.0 · pnpm 11.10.0 · Angular 22.0.5 · WildFly 32.0.1.Final (Jakarta EE 10) · wildfly-maven-plugin 4.2.2.Final · Temurin JDK 21 · macOS. The Windows wrapper script in step 6 was not tested.

1Plugin-level configuration and a stable tool location

Three small changes make the plugin usable for more than the build.

a) Versions and directories move to the plugin-level <configuration>. Settings inside an <execution> only apply to that execution. Command-line calls such as mvn frontend:pnpm … (step 6) run as execution default-cli and only see the plugin-level configuration.

b) The tools move from target/ to .tooling/. mvn clean deletes target/, and with it Node and pnpm. Maven caches the downloads in ~/.m2, so a reinstall is quick, but the IDE's Node interpreter path (step 7) and the pnpmw wrapper (step 6) need a path that stays put.

c) A switch to skip the frontend: -DskipFrontend builds only the Java part. The WildFly dev mode in step 5 uses it.

4The Angular dev server via Maven: profile ng-serve

Add these properties:

…and this profile:

How it works:

  • <defaultGoal>validate</defaultGoal> — mvn -Png-serve needs no goal. Only validate runs: no compilation, no WAR.
  • Three executions, all bound to validate, in this order: install Node and pnpm, run pnpm install, start ng serve. The first two finish in about a second when nothing changed, but they make sure a fresh checkout — or a git pull that brought new dependencies — just works.
  • pnpm start --port … runs the start script of package.json (ng serve); pnpm appends --port to it.
  • BACKEND_URL reaches proxy.conf.mjs as an environment variable; -Dbackend.url=… changes it from the command line.
  • NG_CLI_ANALYTICS=false — the Angular CLI may ask whether to share usage data. Under Maven nobody can answer that prompt and the start would hang.
  • The ng-serve goal keeps running — that is the dev server. Ctrl-C stops Maven and the Node processes together (verified: nothing is left running).

Edit a component and save — the dev server rebuilds in a fraction of a second and pushes the change into the open browser tab:

5The container in dev mode (example: WildFly)

The frontend side does not care how the container runs — it only needs backend.url. Any Jakarta EE 10 container works: one started from the IDE, a local installation, or a Maven-driven dev mode. To stay with "Java and Maven only", this step uses the wildfly-maven-plugin dev goal: it starts WildFly, deploys the application, watches src/main/java and recompiles and redeploys on every change.

How it works:

  • The server comes from Maven Central like any other artifact (wildfly-dist zip), is unpacked into target/ in the initialize phase and stays there — a second start reports wildfly-dist-32.0.1.Final.zip already unpacked.
  • <defaultGoal>initialize wildfly:dev</defaultGoal> — the phase unpacks the server, then the dev goal starts it. The dev goal compiles and deploys the application itself (exploded, as myapp.war).
  • skipFrontend=true — during development the frontend comes from ng serve; the container serves only the REST API.

Run it:

Change a Java class and save — about four seconds later the new code answers.

Port 8080 already taken (another local server)? Start WildFly with a port offset and point the dev server at it:

The offset moves HTTP to 8180 and the management port to 10090; wildfly.port tells the Maven plugin where to find the management interface.

Stopping: Ctrl-C stops Maven and WildFly together. If a server survives anyway (e.g. the terminal was closed), stop it through its management port:

Match WildFly and the JDK. WildFly 32 does not start on Java 25 (Enabling a Security Manager is not supported.); it runs on Java 17 and 21. Use a WildFly version that supports the JDK on your developers' machines.

Variations:

  • Smaller server: instead of unpacking the full distribution, the wildfly-maven-plugin can provision a trimmed server with Galleon (featurePacks + layers, e.g. only jaxrs-server). Same wildfly:dev goal, no unpack execution.
  • Other containers: most have a comparable Maven dev mode (e.g. Open Liberty's liberty:dev). Only backend.url has to match.
  • IDE deployment: if the team already deploys from IntelliJ/Eclipse, keep that and only use mvn -Png-serve.

7IDE setup

IntelliJ IDEA / WebStorm

  • Settings → Languages & Frameworks → Node.js: Node interpreter <project>/.tooling/node/node (Windows: node.exe), package manager <project>/.tooling/node/node_modules/pnpm. Code completion, the Angular language service, running single tests from the gutter — all with the project's versions.
  • Run configurations (type Maven): ng serve with command line -Png-serve, WildFly dev with -Pwildfly-dev. A Compound run configuration starts both with one click.

VS Code

  • Two terminals (mvn -Pwildfly-dev, mvn -Png-serve) or two entries in .vscode/tasks.json with the same commands.
  • Use ./pnpmw … in the integrated terminal for CLI commands.

Unit tests once./pnpmw test
After git pullnothing for the frontend (mvn -Png-serve runs pnpm install); restart -Pwildfly-dev if pom.xml changed
Update Angular./pnpmw ng update @angular/core @angular/cli
Update Node / pnpmchange node.version / pnpm.version in the pom and packageManager in package.json
Deployable WARmvn package → target/myapp.war (frontend built and tested)
Java-only buildmvn package -DskipFrontend

Which URL? During development always http://localhost:4200. The container's own URL (localhost:8080/myapp/) serves whatever frontend build was last copied into the deployment — usually an old one.

9Troubleshooting

SymptomCause / fix
mvn -Png-serve hangs before "Local:"an interactive CLI prompt; keep NG_CLI_ANALYTICS=false in the profile
/api/... returns 404 or 504 on port 4200container not running, or wrong -Dbackend.url (context root included?)
Port 4200 is already in useanother dev server is still running; stop it or use -Dng.port=4300
WildFly: Address already in use (8080 / 9990)another server runs locally → port offset (step 5)
WildFly survives after closing the terminalmvn -Pwildfly-dev wildfly:shutdown
WildFly: Enabling a Security Manager is not supportedWildFly too old for the JDK (step 5)
Build fails with ERR_PNPM_OUTDATED_LOCKFILEpackage.json changed without pnpm-lock.yaml; run ./pnpmw install and commit the lock file
mvn frontend:pnpm … uses wrong directory / versionthe configuration is still inside an <execution>; move it to plugin level (step 1)
Company network: downloads blockedMaven's proxy settings are passed on to pnpm automatically. For a Nexus/Artifactory mirror set <nodeDownloadRoot> / <pnpmDownloadRoot> (and <serverId> for credentials from settings.xml) at plugin level, and registry=… in frontend/.npmrc
